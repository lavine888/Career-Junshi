# 从公开项目开始：首次使用迭代

日期：2026-10-23。本轮观察先于改动：以用户授权的四个公开项目快照，分别让
改动前、改动后的两个新上下文代理完成同一组首次使用请求；每组两轮。未提供
预期答案、问题定位、旧版输出或其他案例。具体模型版本和采样参数未单独记录。

真实项目快照、个人项目选择及实际答复摘录仅留在私有临时工作目录，没有进入
公开仓库。公开案例只用 [四个合成项目](../cases/experiences/public-projects/request.md)，
[示意输出](../cases/experiences/public-projects/example.md)为人工编写，不冒充实际试用。

## 观察到的好处和摩擦

两组首轮都能在没有完整简历、没有具体 JD 时，提供开场项目和可说的方向介绍。
没有把展示仓库、团队参与、fork 或研究结果自动升级成个人工程实现或实际收益。

旧首轮同时安排贡献梳理、口述和寻找两条 JD，作为 30 分钟的完成标准。
第二轮模拟用户表达负担后，旧流程能够收敛为一个设计理解问题；说明已有互动
能力可用，摩擦主要在起步任务的安排，而非需要重做全部证据机制。

## 实际改动

- 入口明确支持“只有 GitHub 也能开始”，优先用现有材料，不要求先填完整简历表。
- 新增 public-projects 参考，由 SKILL 和已有 resume / jd-analysis /
  context-extraction 路径按需选用，保持 1–3 参考预算。
- 只选择少量相关项目，区分公开产物范围与个人贡献，默认分支和版本不能猜。
- 先给可用起点和短介绍，再选一个小结果；时间预算不是塞满任务的要求。
- JD 搜索可以后置；职责想不起来时，从一个可见流程恢复上下文。当前理解不写成
  历史设计贡献。无浏览能力时只要一个有用摘录，不宣称读过链接。
- 沿用来源、主张和隐私规则，没有新 CLI 入口、候选人 schema、自动采集器或记忆。

## 新上下文观察

新首轮把当晚任务收敛到一个项目的一处个人工作，以短介绍为产出，不再要求
当晚找两条 JD。第二轮明确不想找 JD、说不清职责时，继续只围绕一个可见交互
问一道理解题，并保留个人贡献未知，没有倒填职责。

这只是每版各一次会话的观察，不能归因成稳定提升或计算“成功率”。两次首轮
仍偏长；真实候选人的实际贡献必须补充后，才可能形成贡献更具体的成果表述。
公开资料不能独立认证奖项、使用范围或个人作者身份。

## 检查范围

机械检查验证轻量入口、链接、安装资源和既有行为，不把参考文件存在或样例文字
当自然语言质量测试。本轮结果：

- `python -m unittest discover -s tests -v`：275 项通过，111.658 秒。
- `python scripts/validate_skill.py` 与 Skill Creator `quick_validate.py`：通过。
- 临时目录实际安装：新增参考与源文件字节一致，runtime-only 校验通过；
  未复制候选人材料、试用记录或开发案例，未创建记忆。
- `git diff --check`：通过。另行核对新增文档、案例的相对链接。

本轮没有改动 Python 行为或新增以文字存在为断言的测试。上述回归检查与两组
自然语言试用分别报告，不将机械通过解释为对话质量或求职结果已获验证。

## 局限

这是同宿主代理模拟，不是真人首次使用或录用效果实验。固定四项目材料是已选定
的工作集，不代表自动审查了整个 GitHub 账号。没有运行这些项目、播放录屏或
认证团队奖项。合成示意与真实来源试用分别保管；原有安装不自动覆盖或更新。
