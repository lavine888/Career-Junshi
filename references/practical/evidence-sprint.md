# Evidence sprint

Turn one consequential evidence gap into a small, reviewable piece of work.
This is a host-led conversation, not a new decision mode or an automatic build.

## Start from the actual constraint

Reuse the user's target role, existing project, Claim and available materials.
Identify the target wording, missing support, real time budget and next deadline.
Ask only for missing information that changes the plan; do not invent availability.
Seven days is an adjustable planning horizon, not seven days of full-time work.
If an interview is imminent, narrow to existing evidence, safer wording and practice;
do not start a large project to rescue an unsupported resume line.

Choose the smallest artifact that tests this gap: a reproducible evaluation,
an annotated decision, a scoped contribution diff, or a failure analysis. Prefer
existing work and tools. Explain which Claim aspect this could support and which
it cannot; a demo does not establish production use, and code alone does not prove
personal authorship, leadership or improved outcomes.

## Deliver a bounded plan

Deliver `evidence-sprint.md` in chat, or write it only when a file is requested:

- Target Claim / project ID, source and current stage; current safe wording.
- One evidence gap and the exact scope the proposed artifact could support.
- Named deliverable and the minimum contents needed for review.
- Acceptance: command or inspection, inputs, expected observable result, and a
  failure or boundary check. Keep synthetic data and real-world results separate.
- Work blocks whose total fits the stated budget; dependencies and unresolved
  access must be explicit. Replan if time or access changes.
- Stop / reduce scope condition and fallback wording if the gap remains.
- Return path: what artifact, output and contribution boundary to bring back in
  this chat, and what to check before changing the Claim.

All tasks start as planned. Passing an acceptance check establishes only the
stated artifact behavior; it is not a career outcome or evidence certification.
Do not silently expand into a course, a new stack or a portfolio rewrite.

## Review returned work

Inspect only provided or authorized artifacts. Distinguish user-reported results,
inspected files and commands actually run. A path or claimed test pass is not an
inspection. If review is unavailable, say what is unverified and request the
smallest useful excerpt; do not claim the plan was completed.

Keep the project ID, source and original stage in the record. Change the current
stage only when evidence establishes that transition. Update only the supported
Claim aspect, with the new artifact / check as provenance. A local synthetic run cannot
justify a production, metric-improvement or sole-authorship claim. If nothing
supports stronger wording, keep or weaken it and choose one next check.
Close with accepted / missing evidence and one next action. The user can return
later in this chat without enabling persistent memory. Do not read a vault,
initialize memory or save records as part of this experience by default.

If the immediate obstacle is starting rather than designing a project, replace
this playbook with [action-start](action-start.md); do not prescribe a bigger sprint.
