# One project, different role expressions

Use supplied project material and target JDs to change emphasis without changing
facts. This is a host-authored positioning workflow, not a matching score or an
additional decision mode. Read this in place of a less relevant practical reference;
the total reference budget remains 1–3.

## Start from the material

Retrieve the existing project sentence, sources, contribution boundary and target
JDs before asking questions. If the project is missing, ask for one real experience
and what the user personally did. Ask only 1–3 missing details that change wording;
otherwise produce bounded drafts now. The supplied targets determine the number of
versions: one target is sufficient; do not invent roles to fill three versions.

Create one shared fact sheet before writing variants:

- Stable project ID and source IDs / locators; distinguish self-report from checked
  evidence and retain conflicting or unverified attribution.
- Personal actions and decisions, teammates' implementation and AI/tool work.
- Overall project stage, the selected claim's stage and personal contribution stage.
- Actual outputs, observed results, measurement limits and unknowns. No production
  use, improvement, adoption or authorship may be inferred from an artifact's existence.

Keep this sheet invariant across roles. Correct it once if new evidence arrives and
recheck every affected version; a role label cannot upgrade confidence or ownership.

## Translate against actual responsibilities

For each supplied target, identify the exact JD requirement and source. Select only
facts that support that responsibility; explain why each retained fact belongs and
why less relevant or unsupported wording was omitted. Do not add titles, technologies,
metrics, business outcomes, engineering authorship or personal decisions from a JD
or role pack. Relevant role packs may help choose questions, not supply achievements.

If no JD is supplied, label the responsibility mapping a hypothesis based on the
user's target description and name what JD would confirm or change it. Do not claim
current hiring demand or verified fit. A supplied JD establishes what that document
says, not that the vacancy remains open; check fresh sources only when the requested
judgment relies on current availability or market conditions.

Keep roles outside the five role packs under their actual names; leave structured
role_family unknown instead of forcing a nearby family. If evidence cannot support
a distinct version, say so and keep a shared safe sentence or request the decisive
missing material. Different wording need not imply a different accomplishment.

## Deliver role-translation.md

Deliver the report in chat; write a file only when requested, in the user's chosen
directory. Include the shared fact sheet, then for each relevant target:

1. A usable sentence with source references and its self-report / verification boundary.
2. The corresponding JD clause, retained emphasis and reasons for omissions. Keep
   missing requirements separate from demonstrated non-fit.
3. The decisive gap and the smallest check or evidence task that could justify a
   stronger sentence; planned work remains planned.

Finish by checking all versions against the same facts, contribution and stage.
Stop upgrading when evidence runs out. Revisit on a new JD, corrected attribution or
checked result, not merely because another role sounds more attractive. This workflow
does not establish role suitability, hiring probability or a new professional title.
