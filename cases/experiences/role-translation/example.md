# 同一项目的两种岗位表达

**人工编写的合成输出示意，不是实际宿主试用、独立评估或真实求职结果。**
输入见 [request.md](request.md)。两个岗位都能保留评测经历，但现有材料不支持
产品改进成效，也不支持个人集成、部署或生产工程经历。

## 共同事实底稿：P1 文档检索问答原型

| 项目事实 | 来源与边界 |
| --- | --- |
| 本人设计评测用例、检查回答并分类失败；这一轮评测记录已整理完成 | S1 自述，个人作者身份尚未独立核实 |
| 队友实现检索和问答服务；本人未负责服务实现、部署或客户集成 | S1 自述；团队实现不能转给本人 |
| 整体项目仍是迭代中的原型；个人本轮评测已完成 | S1；局部完成不等于整体完成或生产上线 |
| 评测样例记录了答非所问、遗漏来源两类问题 | S2 表格两行，仅支持这些问题曾被记录，不证明发生频率或作者 |
| 无生产使用、用户采用或效果提升数据；无基线及前后对照 | S1、S2；不能生成准确率、用户数或性能改善数字 |

个人贡献按 `SELF_REPORTED` 保留；S2 只支持记录内容，不独立认证 S1 的分工。
J1、J2 是用户提供的合成职责文本，未核验任何真实岗位的招聘状态。

## AI 产品经理

**可用句：** 参与团队文档检索问答原型，负责围绕“回答是否回应问题、是否附来源”
设计评测用例、检查回答并分类失败，整理答非所问、遗漏来源等问题记录；项目仍为
原型阶段。（个人贡献据 S1 自述；检查项及问题记录见 S2。）

| 对应 JD | 保留与删去的理由 |
| --- | --- |
| J1「定义回答质量标准」「评测和失败分析」 | 突出已有评测检查项与失败记录；与实际材料有直接对应 |
| J1「理解用户任务」「形成优先级」「验证改进」 | 暂不写需求验证、优先级决策或推动效果提升；材料未提供这些经历和结果 |

**关键缺口：** 尚无检查项如何来自真实用户任务、如何选择改进优先级的材料。
最小下一步是先核对是否已有任务来源与当时的决策记录；没有就保持未知。之后新做
的用户任务核实或对照评测应注明新时间，不能补写成当时已经完成。

## AI 解决方案工程师

**可用句：** 在团队文档检索问答原型中负责评测用例设计与回答检查，按答非所问、
遗漏来源等问题整理失败记录；检索及问答服务由队友实现，项目尚无生产使用记录。
（个人贡献和实现分工据 S1 自述；失败记录见 S2。）

| 对应 JD | 保留与删去的理由 |
| --- | --- |
| J2「故障分析」「验收方法」 | 保留失败分类和评测这一相关基础，但不把问题分类写成已定位工程根因或完成可复现验收 |
| J2「集成、部署」「生产运行与性能测量」 | 明示队友实现与原型阶段；删去个人集成、客户交付、生产运行和性能优化表述 |

**关键缺口：** 没有本人集成部署的证据，也没有可复现验收步骤或运行测量记录。
可先检查现有评测表能否补足输入、检查标准与复现步骤；这只能支持评测可复现性。
如果要证明集成能力，需要另做有明确个人贡献的集成任务并验证，不能把队友实现
改写为本人经历；本地演示也不能直接写成生产交付。

## 交付检查

两版保留同一项目、同一贡献与同一阶段，差别只在与 J1、J2 对应的重点。
当前可以使用这些有自述边界的句子；“改进了产品效果”“独立实现服务”“完成客户
部署”均不能写。新 JD、分工更正或真实验收结果出现后，再更新底稿及相关版本。
